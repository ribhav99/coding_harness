# Work-Orders Loop

## Overview

The Work-Orders Loop is the third autonomous stage. It reads approved blueprints from `blueprints/` and produces a flat list of slug-named work orders under `work-orders/`, plus a separate `_sequence.md` file that records the execution order. A single autonomous generator writes the work-order tree; four reviewer subprocesses evaluate the tree against distinct rubrics; the orchestrator and the agents communicate bidirectionally through `work-orders_communication/`; the orchestrator commits the tree on full pass.

The operator needs this loop because work-order decomposition is where blueprint scope becomes implementation scope. Sloppy decomposition either leaves gaps (a blueprint section that no work order produces), creates overlap (two work orders both claiming the same interface and conflicting at execution time), gets the sequence wrong (work orders that depend on output that hasn't been produced yet), or under-specifies a work order so the per-WO coding agent doesn't know what it's actually meant to do. The loop solves these with four reviewers focused on the failure modes that propagate downstream into the coding loop: structural conformance + content quality, blueprint-to-work-order coverage, no-overlap of produced surface, and sequencing correctness.

The work-orders loop is the third in the upstream-loop family (PRD authoring → requirements loop → blueprint loop → work-orders loop → coding loop), all sharing the gen+reviewer cycle, communication-folder mechanism, dual completion condition, and `awaiting_clarification` exit verdict. The coding loop that follows is execution-only — its per-work-order subprocesses communicate through the PR (commits + PR comments), not a communication folder.

## Terminology

- **Work order** — one `work-orders/wo-<slug>.md` file (the visible scoped-task body) plus a sibling `.wo-<slug>.meta.yaml` (orchestrator-managed meta). The slug is a stable, human-readable, kebab-case identifier; once chosen, it never changes (renaming a slug breaks every cross-reference that points to it). Work orders live flat at the work-orders root; there are no per-WO subdirectories.
- **Scoped-task body** — the canonical markdown shape of `wo-<slug>.md`, pinned in §REQ-WO-002 (Goal; Blueprints; In scope; Out of scope; Produces; Depends on; Acceptance criteria; Gates; optional Implementation notes).
- **Mention syntax** — two cross-artifact link types: `#<blueprint-slug>` for references to a blueprint (resolves to `blueprints/{containers,components,features}/<blueprint-slug>.md`); `@wo-<slug>` for references to another work order by ID.
- **Structured block** — a fenced ` ```yaml ` block with required keys, used inside `## Produces`, `## Depends on`, and `## Gates` sections. The block is YAML-shaped so reviewers and the orchestrator can parse it mechanically.
- **Acceptance criterion** — one binary checklist item with three pieces: an ID (`AC-WO-<slug>.M`), an observation gate (`tests` | `playwright` | `code-spec` — bare gate keys matching the keys in `## Gates`), and a one-sentence expected outcome.
- **Atomicity** — a work order produces one cohesive change: at most one named interface in the `Produces` block (or two-to-three tightly cohesive entries that compose into one delivered surface), or (for refactor-only work orders that produce nothing) one cohesive purpose stated in the `Goal` sentence. A `Goal` sentence that requires "and" to describe the change is a sign the work order should be split.
- **Type** — `.wo-<slug>.meta.yaml.type` is one of `feature`, `refactor`, `bug-fix`, `infra`, or `operator-action`. The first four are agent-executable. `operator-action` is reserved for work the operator must do themselves (set up OAuth credentials, obtain sample data, run a one-time external configuration step); the orchestrator never spawns a coding-loop agent for an `operator-action` work order.
- **Status** — `.wo-<slug>.meta.yaml.status` is one of `backlog`, `ready`, `in_progress`, `done`, or `blocked_external`. `blocked_external` is set by the per-WO coding agent when it discovers mid-execution that it cannot proceed without operator action; the orchestrator skips `blocked_external` work orders on `pick_next` and surfaces them in `work-orders/_external-blockers.md`.
- **`_sequence.md`** — `work-orders/_sequence.md` lists every work order's slug in execution order, top to bottom. Mutable. Operator may re-order; the orchestrator's `pick_next` walks top to bottom and selects the first work order whose `status: ready`, whose `blocked_by[]` are all `done`, and whose `type` is not `operator-action`.
- **`_external-blockers.md`** — `work-orders/_external-blockers.md` is the operator-readable summary of every work order requiring operator action. Two sections: anticipated (work orders with `type: operator-action`) and discovered mid-execution (work orders with `status: blocked_external`). Single file; operator scans it once to see everything they need to do.
- **`.sequence.meta.yaml`** — `work-orders/.sequence.meta.yaml` records the hash of the blueprint tree at the time the sequence was generated plus a generation timestamp; used to short-circuit regeneration when blueprints have not changed.
- **Open question** — a decomposition ambiguity the generator cannot resolve autonomously and has appended to `work-orders/_questions-pending.md` for operator answer. Bare-question shape only (like the requirements loop), since work-order decomposition asks the operator to clarify a source artifact, not to pick between options.
- **Communication folder** — `work-orders_communication/` at the project root, sibling to `work-orders/`. One markdown file per agent in the loop (one for the generator, one per reviewer); both sides read and append.
- **Dual completion condition** — the pass condition for this loop: all four reviewers pass AND `work-orders/_questions-pending.md` has zero unanswered questions.
- **`awaiting_clarification`** — the loop exit verdict when reviewers pass on the current content but open questions remain and the generator can make no further progress without them. Same verdict as the requirements and blueprint loops.

## Requirements

### REQ-WO-001 — Loop orchestrator subcommand
**User Story.** As an operator, I want a single CLI command that runs the full work-orders loop, so that I can go from approved blueprints to a reviewed work-order tree (or to a scannable questions file) in one autonomous pass.
- **AC-WO-001.1** — When the operator runs `python -m orchestrator work-orders-loop`, the orchestrator shall spawn one generator subprocess, then spawn each reviewer subprocess, parse the trailing `VERDICT:` line from each reviewer's stdout, and commit the work-orders tree on full `pass` or on `awaiting_clarification`.
- **AC-WO-001.2** — The orchestrator shall re-spawn the generator on any reviewer fail; the generator reads each reviewer's communication file directly to see prior reviews and its own prior responses, so the orchestrator does not assemble a separate retry-context block.
- **AC-WO-001.3** — The orchestrator shall enforce an attempt cap per invocation and a wall-clock cap per subprocess and exit with an `exhausted` verdict if either is hit.
- **AC-WO-001.4** — The work-orders-loop subcommand shall be independent of the coding-loop subcommand; running `work-orders-loop` shall produce or refresh the work-order tree without executing any per-work-order implementation.

### REQ-WO-002 — Work-order document shape
**User Story.** As a reviewer (and as a downstream coding-loop generator), I want every work order to follow a single canonical shape, so that scoping checks and execution prompts can read the same information from the same place.
- **AC-WO-002.1** — Each work order's `wo-<slug>.md` shall consist of the following sections in this order: `# <Title>`, `## Goal`, `## Blueprints`, `## In scope`, `## Out of scope`, `## Produces`, `## Depends on`, `## Acceptance criteria`, `## Gates`, optional `## Implementation notes (non-binding)`.
- **AC-WO-002.2** — `## Goal` shall contain exactly one observable-outcome sentence describing what the work order delivers. The sentence shall be specific, not vague — "improve performance" is not a Goal; "`POST /search` 95th-percentile latency below 200ms with 10k indexed documents" is.
- **AC-WO-002.3** — `## Blueprints` shall list one bullet per referenced blueprint, in the form `- #<blueprint-slug> — <one line on what this work order contributes>`. Every `#<blueprint-slug>` mention shall resolve to an existing file in `blueprints/{containers,components,features}/<blueprint-slug>.md`.
- **AC-WO-002.4** — `## In scope` and `## Out of scope` shall each be a bullet list. `Out of scope` shall be non-empty when the boundary is non-obvious — its purpose is to name things a reasonable reader might assume are included but are not.
- **AC-WO-002.5** — `## Produces` shall hold a single fenced ` ```yaml ` block listing the interfaces this work order makes available to downstream work orders. Each list entry shall have three required keys: `kind` (one of `endpoint`, `function`, `module`, `type`, `migration`, `config`, `doc`, `test-fixture`), `name` (a concrete identifier), and `contract` (a one-line input/output description or signature detailed enough that a downstream work order can consume the interface without reading this work order's body). A work order with no produced interfaces shall use an empty list `[]`; a refactor-only work order is the typical empty-list case.
- **AC-WO-002.6** — `## Depends on` shall hold a single fenced ` ```yaml ` block with two top-level keys: `work_orders` (a YAML list of `wo-<slug>` IDs this work order depends on) and `interfaces` (a YAML list of `{from: wo-<slug>, name: <interface-name>}` entries). Either list may be empty (`[]`). The `work_orders` list shall be the source of truth for `.wo-<slug>.meta.yaml.blocked_by[]`; the orchestrator materialises `blocked_by[]` from this block.
- **AC-WO-002.7** — `## Acceptance criteria` shall hold a checklist; each criterion shall be on its own line in the format `- [ ] AC-WO-<slug>.M (via <gate>) — <expected outcome>`, where `<slug>` matches the work-order slug, `M` increments from 1 within the work order, `<gate>` is one of the gate keys declared in `## Gates` (`tests`, `playwright`, or `code-spec`), and `<expected outcome>` is one binary sentence. Each criterion shall be concrete and verifiable, never vague — "the system works" is not an AC; "`POST /sign-in` with valid credentials returns 200 and a `SessionToken` payload" is.
- **AC-WO-002.8** — `## Gates` shall hold a single fenced ` ```yaml ` block with six required keys: `tests`, `playwright`, `code-spec`, `code-regression`, `code-security`, `code-quality`. Each key's value shall be either `required` or `not_applicable`. `code-spec`, `code-regression`, `code-security`, and `code-quality` shall always be `required`; `tests` and `playwright` may be `not_applicable` (e.g. `playwright: not_applicable` for a pure-library work order, `tests: not_applicable` for a doc-only work order).
- **AC-WO-002.9** — `## Implementation notes (non-binding)` is optional. When present, it carries pointers about files likely involved or constraints worth flagging. It shall never prescribe an implementation; the per-work-order coding-loop generator owns implementation choices.

### REQ-WO-003 — Generator reads blueprints and produces the work-order tree
**User Story.** As an operator, I want the generator to read every approved blueprint and produce a flat dependency-ordered tree of work orders, so that the full delivery surface is decomposed without me writing any of the work orders by hand.
- **AC-WO-003.1** — The generator shall be a `claude -p` subprocess running with the `blueprint-to-work-orders` skill — single skill, no sub-skill co-invocation. The generator writes the full scoped-task body for each work order directly; there is no separate "stub then expand" step.
- **AC-WO-003.2** — The generator shall read every approved blueprint under `blueprints/`, the existing `work-orders/` tree (every `wo-<slug>.md` plus `_sequence.md` if present), the current `work-orders/_questions-pending.md` (if any), and `work-orders/.sequence.meta.yaml` (if any) before deciding what to produce or edit.
- **AC-WO-003.3** — The generator shall write each work order to `work-orders/wo-<slug>.md` following the document shape pinned in REQ-WO-002. Slugs shall be stable kebab-case identifiers (e.g. `wo-add-signin-endpoint`); once chosen, a slug is never renamed (renaming a slug breaks every cross-reference that points to it).
- **AC-WO-003.4** — The generator shall update `work-orders/_sequence.md` to list every work order's slug in a valid topological order — top to bottom is the execution order. The format is a numbered markdown list with each entry as a backticked `wo-<slug>` ID. The sequence is mutable; the operator may re-order it manually before re-running the loop. The generator's job is to produce a valid initial sequence; preserving operator re-orderings on subsequent runs is also expected (only re-order entries when the dependency graph requires it).
- **AC-WO-003.5** — When a work order represents work the operator must do themselves (set up OAuth credentials, obtain sample data, run a one-time external configuration step), the generator shall mark it `type: operator-action` in the meta. Operator-action work orders are still real work orders with full Goal / In scope / Out of scope / Acceptance criteria sections, so the operator knows what done looks like.
- **AC-WO-003.6** — The generator shall be iterative: on every invocation it reads the existing tree first and edits only what needs changing rather than regenerating from scratch. It shall preserve operator edits (added Out-of-scope items, refined Goal sentences, manually-seeded work orders) when they don't conflict with blueprint changes.
- **AC-WO-003.7** — Before generating, the generator shall compare the current blueprint-tree hash to the hash recorded in `work-orders/.sequence.meta.yaml`. If the hashes match and there are no failing reviews from a prior attempt to address, the generator shall produce no edits and exit; the orchestrator then runs reviewers on the existing tree and, if all pass, exits with a `pass` verdict. If the hashes differ or there are failing reviews to address, the generator shall regenerate or refine the tree.
- **AC-WO-003.8** — On full `pass`, the orchestrator shall update `.sequence.meta.yaml` with the current blueprint-tree hash and a generation timestamp.

### REQ-WO-004 — Non-blocking clarification questions
**User Story.** As an operator, I want the generator to bubble up decomposition ambiguities without stalling, so that I can answer them at my own pace while the loop continues producing everything that does not depend on the open question.
- **AC-WO-004.1** — When the generator hits a decomposition ambiguity it cannot resolve autonomously (e.g. a blueprint references a capability without specifying its boundary, or two blueprints describe overlapping responsibilities without stating which work order owns which slice), it shall append a structured block to `work-orders/_questions-pending.md`. The generator does this directly; there is no separate bubble-up skill.
- **AC-WO-004.2** — Question blocks shall use the bare-question shape only: title, where (the affected blueprint slug or section), what's ambiguous / what's needed, what would unblock, blank `Your answer:`. The generator shall not synthesize options to choose between; the resolution is the operator clarifying a source artifact (typically a blueprint or, more rarely, a work order they want to seed manually).
- **AC-WO-004.3** — After appending a block, the generator shall continue producing every work order that does not depend on the open question.
- **AC-WO-004.4** — The generator shall not stop or exit on an open question; appending and continuing is the only allowed response.
- **AC-WO-004.5** — Where an open question affects a work order, the generator may leave a brief `<!-- pending: <question-title> -->` HTML comment at the affected location; reviewers shall not flag these comments as defects.

### REQ-WO-005 — Reviewer-generator communication channel
**User Story.** As an operator, I want the generator and reviewers to communicate bidirectionally through visible files, so that I can read the conversation and so the generator can push back on findings it disagrees with.
- **AC-WO-005.1** — The orchestrator shall maintain a communication folder at the project root: `work-orders_communication/` — sibling to `work-orders/`, not nested inside it.
- **AC-WO-005.2** — The communication folder shall contain one markdown file per agent in the loop: `blueprint-to-work-orders.md` (generator outbound) plus one per reviewer (`wo-spec-judge.md`, `wo-coverage-judge.md`, `wo-overlap-judge.md`, `wo-sequencing-judge.md`).
- **AC-WO-005.3** — The orchestrator shall ensure the communication folder exists before spawning the generator (mkdir-with-exists-ok). The folder shall never be wiped — it accumulates the full reviewer-generator conversation across attempts and across invocations forever.
- **AC-WO-005.4** — The generator shall read every reviewer's file in the communication folder before producing or editing artifacts. On retry attempts (attempts ≥ 2), the generator shall append per-finding responses (fix / push back / surface to operator) to each failing reviewer's file and a `## Changes since previous attempt` block to every reviewer's file.
- **AC-WO-005.5** — Each reviewer shall read its own communication file and the artifacts it judges, run its review, and **append** a `## Review` block to the same file. The reviewer's stdout shall be a short acknowledgement ending with a single trailing line of exactly `VERDICT: pass` or `VERDICT: fail`.
- **AC-WO-005.6** — Reviewers shall preserve all prior content — when a reviewer uses the Write tool to record its review, every byte of existing file content shall be included unchanged above the new block; reviewers never overwrite or modify content already in the file.
- **AC-WO-005.7** — Race-free by sequential execution: the orchestrator runs generator → reviewers → generator → reviewers strictly sequentially per attempt; reviewers run in parallel within an attempt but each writes only its own dedicated file. No two processes ever write the same file concurrently.
- **AC-WO-005.8** — At every attempt boundary and on every loop-exit verdict (`pass`, `awaiting_clarification`, `exhausted`), the orchestrator shall snapshot each `<reviewer-name>.md` from the live communication folder into `harness/state/reviews/work-orders-loop/attempt-<N>/<reviewer-name>.md`.
- **AC-WO-005.9** — On every loop-exit verdict (`pass`, `awaiting_clarification`, `exhausted`), the live communication folder shall be left in place. Re-running the loop after any exit verdict picks up the prior conversation as context for the next attempt; the per-attempt snapshots under `harness/state/reviews/<loop>/attempt-<N>/` provide the frozen audit trail alongside.

### REQ-WO-006 — Four reviewer subprocesses
**User Story.** As an operator, I want the work-order tree checked against four distinct rubrics, so that structural defects, coverage gaps, produced-surface overlaps, and sequencing errors are all caught before any execution begins.
- **AC-WO-006.1** — The orchestrator shall spawn `wo-spec-judge` to verify every work order's structural conformance and content quality. Specifically: sections present in canonical order; fenced ` ```yaml ` blocks parse and have required keys; AC rows match `AC-WO-<slug>.M (via <gate>) — <outcome>` format; Goal is one observable, non-vague sentence; In/Out scope concrete and non-contradictory; produced interface contracts are detailed enough that a downstream work order could consume them; AC rows are concrete and binary, never vague; implementation notes useful or absent, never prescriptive; atomicity rule (one cohesive change per work order); no refactor breadcrumbs. Fanned out per-work-order so failures are attributable.
- **AC-WO-006.2** — The orchestrator shall spawn `wo-coverage-judge` to verify three things: (a) every approved blueprint's delivery surface (component blocks, model blocks, feature commitments) maps to at least one work order via a `#<blueprint-slug>` mention; (b) every `#<blueprint-slug>` mention in any work order resolves to an existing file in `blueprints/{containers,components,features}/<blueprint-slug>.md`; (c) every acceptance criterion declares an observation gate (`tests`, `playwright`, or `code-spec`) that the gate set in `## Gates` actually declares `required`.
- **AC-WO-006.3** — The orchestrator shall spawn `wo-overlap-judge` to verify no two work orders' `## Produces` blocks list entries with the same `kind` + `name` pair. Exactly one work order shall produce a given interface; if two claim production of the same `kind`+`name`, that is a finding (the implementing agent for the second work order will conflict with the first's output).
- **AC-WO-006.4** — The orchestrator shall spawn `wo-sequencing-judge` to verify both **structural** and **semantic** sequencing correctness. Structural: (a) the dependency graph derived from each work order's `Depends on.work_orders` is acyclic; (b) every `Depends on.interfaces` entry resolves to a `Produces` entry in the named upstream work order; (c) `_sequence.md` lists every work order in a valid topological order of the dependency graph (no work order appears before any of its declared dependencies). Semantic: (d) for each declared dependency, does the dependent work order actually consume the upstream's output (vs. an unnecessary or fabricated dependency); (e) are there missing dependencies (a work order needs another's output but didn't say so); (f) could the sequence be tightened (a work order positioned later than necessary). Semantic findings are flagged with reasoning, not just structural verdicts.
- **AC-WO-006.5** — Each reviewer subprocess shall run with `--disallowedTools Bash,NotebookEdit`. `Write` and `Edit` are allowed so the reviewer can append to its own communication file; a `PreToolUse` path-guard hook shall block any `Write`/`Edit` call whose target path is not exactly the reviewer's own `work-orders_communication/<reviewer-name>.md` file.
- **AC-WO-006.6** — Each reviewer's stdout shall end with a single trailing line matching exactly `VERDICT: pass` or `VERDICT: fail`; a `Stop` hook shall block completion if the trailing line is missing or malformed.

### REQ-WO-007 — Dual completion condition
**User Story.** As an operator, I want the loop to exit `awaiting_clarification` when open questions remain, so that I know when to clarify a source artifact versus when the work-order tree is fully accepted.
- **AC-WO-007.1** — Full `pass` shall require both all four reviewers pass AND `work-orders/_questions-pending.md` has zero unanswered questions.
- **AC-WO-007.2** — When reviewers pass on the current state but open questions remain and the generator can make no further progress without them, the orchestrator shall exit with verdict `awaiting_clarification`, commit current progress (work orders with optional `<!-- pending: -->` markers and the updated questions doc), write a history entry, and print an operator-facing summary of the open questions.
- **AC-WO-007.3** — `awaiting_clarification` shall not be treated as a failure state; re-running the loop after the operator has clarified the relevant source artifact (typically a blueprint, occasionally a manually-seeded work order) shall resume from the current work-order state. This is the same verdict and mechanism the requirements and blueprint loops use — only the file location (`work-orders/_questions-pending.md`) differs.

### REQ-WO-008 — Operator-side question resolution
**User Story.** As an operator, I want to resolve open questions by clarifying source artifacts, so that the next loop run consumes the clarification and continues.
- **AC-WO-008.1** — The operator shall resolve a question by editing the source artifact named in the question's `Where:` field (typically a blueprint, occasionally a manually-seeded work order or a `In scope`/`Out of scope` ambiguity in an existing work order). The question block can then be deleted or moved to `_questions-resolved-<timestamp>.md` for git-history audit.
- **AC-WO-008.2** — On the next loop run, the generator shall re-read the questions doc and the now-clarified source artifacts and pick up where it left off.

### REQ-WO-009 — Verdict aggregation and retry
**User Story.** As an operator, I want the orchestrator to decide retry vs pass vs exhaust deterministically, so that the loop converges without operator intervention when the blueprint inputs and answered questions are clear enough.
- **AC-WO-009.1** — The orchestrator shall parse only the trailing `VERDICT:` line from each reviewer's stdout to decide pass or fail. The full review prose lives in the communication file (§REQ-WO-005); the orchestrator does not parse that body for control flow.
- **AC-WO-009.2** — On any reviewer fail, the orchestrator shall re-spawn the generator. The retry prompt names only the failing reviewers; the generator reads each reviewer's file directly and decides which findings to fix and which to push back on.
- **AC-WO-009.3** — The orchestrator shall apply a `Stop` hook on reviewer subprocesses that validates the reviewer's final chat message ends with a single trailing line matching exactly `VERDICT: pass` or `VERDICT: fail`; the hook shall block completion if the trailing line is missing or malformed (in-session enforcement layer). If a reviewer subprocess does exit with malformed stdout despite the hook, the orchestrator records that reviewer's verdict as `fail` for aggregation and the loop continues — there is no post-exit recovery layer.

### REQ-WO-010 — Artifact commit and audit trail
**User Story.** As an operator, I want the approved work-order tree committed to git, so that git history is the audit trail and no PR is needed for upstream-loop output.
- **AC-WO-010.1** — On full `pass` and on `awaiting_clarification`, the orchestrator shall commit the work-orders tree (every `wo-<slug>.md`, every `.wo-<slug>.meta.yaml` materialised from the `Depends on` block, the updated `_sequence.md`, the updated `_external-blockers.md`, the updated `.sequence.meta.yaml`, and the updated `_questions-pending.md`).
- **AC-WO-010.2** — The orchestrator shall not open a pull request for the work-orders tree.
- **AC-WO-010.3** — The orchestrator shall record loop-level iteration history in `harness/state/work-orders-loop.json` and snapshot the final attempt's communication folder into `harness/state/reviews/work-orders-loop/attempt-<N>/`.
- **AC-WO-010.4** — On full `pass`, all produced agent-executable work orders (any `type` other than `operator-action`) shall land with `status: ready` in their `.wo-<slug>.meta.yaml`. Operator-action work orders shall land with `status: ready` as well — `ready` here means "ready for the operator to do" — but the orchestrator's coding-loop drain skips them per `type`.

### REQ-WO-011 — Operator-action work orders and external-blocker visibility
**User Story.** As an operator, I want a single scannable surface listing every work order that needs my attention — both anticipated operator-action items and items the agent discovered it couldn't do — so I always know what's blocking the loop from draining further.
- **AC-WO-011.1** — `work-orders/_external-blockers.md` shall be present whenever any work order has `type: operator-action` (with `status` not `done`) OR `status: blocked_external`. When neither condition holds, the file shall be absent or empty.
- **AC-WO-011.2** — The file shall have two sections: **"Anticipated operator actions"** listing every work order with `type: operator-action` and `status: ready`, and **"Discovered mid-execution blockers"** listing every work order with `status: blocked_external`. Each entry shall include the work-order slug as a backticked link, the Goal sentence, the AC summary, and (for discovered blockers) the prose explanation the agent left when it transitioned to `blocked_external`.
- **AC-WO-011.3** — The orchestrator shall regenerate `_external-blockers.md` on every loop-exit verdict (`pass`, `awaiting_clarification`, `exhausted`) by walking every work order's meta. The operator does not edit this file directly; the operator clears blockers by completing the action and editing the affected work order's `.wo-<slug>.meta.yaml.status` to `done` (for operator-action) or `ready` (for blocked_external), at which point the next regeneration drops the entry from `_external-blockers.md`.

## Feature Behavior & Rules

The work-orders loop is a near-symmetric mirror of the blueprint loop. Same dual-completion mechanism, same `awaiting_clarification` exit verdict, same gen↔reviewer communication-folder pattern. The differences are: a different generator skill (`blueprint-to-work-orders` instead of `frd-to-blueprint`), a different reviewer set (four `wo-*` judges rather than four `bp-*` judges focused on different concerns), a different artifact tree (`work-orders/` rather than `blueprints/`), and a question shape restricted to bare (no with-options blocks) since work-order decomposition resolves to clarifying source artifacts, not picking architectural alternatives. Everything else — orchestrator flow, communication-folder lifecycle, snapshot semantics, attempt caps, exit verdicts — is identical.

The work-order document shape is the load-bearing contract for everything downstream. The seven structural elements — Goal, Blueprints, In/Out scope, Produces, Depends on, Acceptance criteria, Gates — are what the work-orders-loop reviewers check, what the per-work-order coding-loop generator reads, and what the per-work-order coding-loop reviewers (`code-spec-judge` in particular) verify against the diff. Loose prose at this stage produces unverifiable execution downstream.

The structured `Produces` and `Depends on` blocks turn what would otherwise be human prose into a machine-readable dependency graph. `wo-sequencing-judge` resolves every `interfaces` entry in `Depends on` to a concrete entry in the upstream work order's `Produces`; if the resolution fails, the dependency is broken before any code is written. The `.wo-<slug>.meta.yaml.blocked_by[]` field is materialised by the orchestrator from `Depends on.work_orders` so there is one source of truth — the description.

Sequencing happens at authoring time, not at pick-next time. The generator decides what each work order produces, what it depends on, and what valid topological order to put them in. The orchestrator's `pick_next` is then trivial: walk `_sequence.md` top to bottom and select the first work order whose `status: ready`, whose `blocked_by[]` are all `done`, and whose `type` is not `operator-action`. The intelligence lives in the generator; the mechanics live in the orchestrator. The sequencing judge verifies both — structurally (the graph is acyclic, references resolve, `_sequence.md` is a valid topological sort) and semantically (each declared dependency reflects a real consumption; no missing dependencies; the order is tight).

The sequence file is mutable. The operator may re-order `_sequence.md` to push a particular work order earlier (because they want to validate one slice of the project first) or later (because they want to defer something). The sequencing judge catches re-orderings that violate the dependency graph; everything else is operator's prerogative. Slug-named work orders mean re-ordering is one-file edit; nothing has to be renamed.

The acceptance-criteria schema turns each criterion into a row a reviewer can iterate. `AC-WO-<slug>.M (via tests) — Outcome` makes three things explicit: which work order owns the criterion (`<slug>`), which gate verifies it (`tests`), and what the criterion expects (binary outcome). `code-spec-judge` walks the checklist mechanically rather than guessing what the work order's prose intended.

The gate declaration block makes per-work-order verification explicit. The orchestrator does not infer "is this work order UI-shaped?" from the description; it reads `## Gates`. `playwright: not_applicable` is the explicit signal to skip Playwright; `tests: not_applicable` is the explicit signal for a doc-only work order. The four LLM-as-judge gates (`code-spec`, `code-regression`, `code-security`, `code-quality`) are always `required` because the failure modes they catch (spec drift, regression, security, quality) apply to every diff regardless of work-order shape.

Atomicity is part of the rubric `wo-spec-judge` enforces. The structural anchor is one entry in `Produces` for an interface-producing work order, or one cohesive purpose stated in `Goal` for a refactor-only work order with empty `Produces`. The surface heuristic is the `Goal` sentence — if the change requires "and" to describe, it is two work orders, not one. Sloppy atomicity at this stage means the per-work-order coding agent gets a fuzzy target and either does too much (touching code outside the intended slice and tripping `code-regression-judge`) or too little (leaving the next work order to clean up).

Coverage is what `wo-coverage-judge` enforces. The union of all `Produces` plus all `In scope` items across all work orders has to compose into the full delivery surface of every approved blueprint. Gaps mean some blueprint section never gets implemented; `wo-coverage-judge` catches them. Overlap is a different concern (two work orders both claim the same produced interface) and is caught separately by `wo-overlap-judge`.

`wo-overlap-judge` is the simplest of the four: for every pair of work orders, scan their `Produces` lists; if any `kind`+`name` pair appears in both, flag it. Exactly one work order owns a given interface; the duplication signals a decomposition mistake (the generator either split a work order it shouldn't have or duplicated an interface across two work orders that should be one).

`wo-sequencing-judge` does the heavy lift on order correctness. The structural part (acyclic, references resolve, `_sequence.md` is a valid topological sort) is mechanical. The semantic part (does each declared dependency reflect a real consumption; are there missing dependencies; could the sequence be tightened) requires judgment about what each work order actually needs from its predecessors. This is where most of the value is — a structurally-valid graph that misses a real dependency will pass the structural check and fail in production when the implementing agent discovers `wo-Y` needs `wo-X`'s output but `wo-X` hasn't run.

The `awaiting_clarification` exit is not failure — it is the loop's signal that decomposition has hit an ambiguity in a source artifact. The operator's job is to clarify the blueprint (or, occasionally, to seed a manually-authored work order). The next loop run consumes the clarification, the generator continues, and the cycle terminates when the questions doc is empty and all reviewers pass.

The communication folder makes the gen↔reviewer back-and-forth visible and durable. Without it, every attempt is a one-shot exchange — the generator writes, reviewers judge, the generator gets aggregated feedback through orchestrator-assembled prompts. With it, the conversation persists across attempts, the generator can push back on a specific reviewer by appending to that reviewer's file, and the reviewer sees the push-back and may revise its position. The orchestrator stays small — it spawns subprocesses and reads `VERDICT:` lines; the bidirectional content lives where both sides can see it.

Operator-action work orders and `blocked_external` status are the harness's escape valve for work the agent literally cannot do. Anticipated operator-action work orders (set up OAuth, obtain sample data) are flagged at authoring time by the generator with `type: operator-action` so the operator sees them in `_external-blockers.md` from the start. Discovered blockers (the agent picks up a normal work order, gets to a step it can't autonomously do, and exits) transition the work order to `status: blocked_external` and append to `_external-blockers.md` so the operator can clear the block. Both surfaces flow through the same operator-readable file; the operator clears them by completing the action and updating the work order's status to `done` (for operator-action) or `ready` (for blocked_external).

The work-orders loop is the third in the upstream-loop family. The progression is PRD authoring → requirements loop → blueprint loop → work-orders loop → coding loop. The first three autonomous loops share the upstream-loop pattern (gen + reviewers, communication folder, awaiting_clarification, no PR for output); the coding loop that follows is execution-only (per-work-order subprocess, PR-based comms, no communication folder).
