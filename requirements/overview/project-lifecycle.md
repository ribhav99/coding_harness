# Project Lifecycle

One project moves through five stages end to end: a manual PRD-authoring stage followed by four autonomous loops. The first three autonomous loops (requirements, blueprint, work-orders) are *upstream* loops: each shares the same core mechanic — orchestrator spawns a generator, then spawns each reviewer, aggregates verdicts, re-spawns the generator with aggregated feedback on any fail, commits the artifact on all-pass, supports a non-blocking clarification mechanism that exits with `awaiting_clarification` when source artifacts need to be clarified. They share state-file plumbing, communication-folder plumbing, reviewer review snapshots, dual completion condition, and budget enforcement. They differ in generator skill, reviewer set, target artifact tree, and which file location holds open questions. The fourth autonomous loop (coding) is *execution-only* — per-work-order subprocess, PR-per-work-order flow, no communication folder.

**Stage 1 — Manual PRD authoring.** The operator opens a Claude Code session, invokes the `prd-authoring` skill, and drafts a single `PRD.md` at the project repo's root. One monolithic document in prose. The skill wears a senior-PM role with feature-unit scoping discipline, a clarification policy (ambiguous → ask and wait; specific → act; middle → propose plus up to two questions), overview-style writing rules (narrative prose, active voice, no fluff, WHAT not HOW), and no-fabrication and no-refactor-breadcrumb discipline. Critique is conversational inside the same session — the operator asks "what's missing?" or "critique this section" and the skill applies a five-category rubric (CONFLICT, MISSING, AMBIGUOUS, DUPLICATION, STALE) filtered to critical-only findings. Authoring the PRD is the human's job; there is no autonomous loop at this stage. When the PRD is ready, the operator triggers the Requirements Loop.

**Stage 2 — Requirements Loop (autonomous).** Triggered by `python -m orchestrator requirements-loop`. The generator reads `PRD.md` and decomposes it into the full structural tree under `requirements/`. Two output surfaces: product-overview sections (flat inside `requirements/overview/`) and Feature Requirements Documents (flat inside `requirements/features/`, with `<slug>_children/` subdirectories for child features). The generator is iterative — it reads any existing overview and features trees first and only edits what needs changing. When the PRD itself is genuinely ambiguous, the generator appends a structured block to `requirements/_questions-pending.md` and keeps working on everything that is not blocked. Four reviewer subprocesses run after the generator exits: structural spec, cross-doc consistency, PRD coverage, and feature scoping. Completion is dual: full `pass` requires all reviewers pass AND `_questions-pending.md` has no open questions blocking the review. If reviewers pass on the concrete parts but open questions remain, the loop exits `awaiting_clarification`, the artifact is committed, and the operator resolves the questions by editing `PRD.md` before re-running.

**Stage 3 — Blueprint Loop (autonomous, non-blocking clarification questions).** Triggered by `python -m orchestrator blueprint-loop`. A single generator running the `frd-to-blueprint` skill produces three kinds of blueprints — container blueprints for deployable runtimes, component blueprints for cross-cutting reusable capabilities (auth, notifications, file storage, observability), and feature blueprints slug-matched 1:1 with each FRD. When the generator hits an architectural choice that requires operator judgment — tech stack, framework, hosting model, auth provider, ORM, major architectural pattern — it does not stop. It appends a structured block to `blueprints/_questions-pending.md`, picking one of two shapes: a bare question (when the answer isn't a choice between alternatives) or a question with two-to-four pre-researched options each with pros and cons plus a recommended default (when the choice is genuine). The generator keeps working on everything not blocked by the open question. Four reviewer subprocesses run after the generator exits: structural spec, FRD-to-blueprint coverage, cross-blueprint consistency, and decision hygiene. They communicate bidirectionally with the generator via files in `blueprints_communication/` at the project root — one file per agent, append-only conversation transcripts. Completion is dual: full `pass` requires all reviewers pass AND `blueprints/_questions-pending.md` has zero unanswered questions. If reviewers pass on the concrete parts but open questions remain, the loop exits `awaiting_clarification` (same verdict as the requirements loop), the operator answers at their leisure, and re-running picks up where the loop left off.

**Stage 4 — Work-Orders Loop (autonomous, non-blocking clarification questions).** Triggered by `python -m orchestrator work-orders-loop`. A single generator running the `blueprint-to-work-orders` skill reads `blueprints/` and produces a flat tree of slug-named work orders under `work-orders/` (one `wo-<slug>.md` plus `.wo-<slug>.meta.yaml` per work order, no per-WO directories), plus a separate `_sequence.md` recording the execution order. No phases — one continuous task sequence with `Depends on.work_orders` plus `_sequence.md` encoding dependencies. Each work order's `wo-<slug>.md` follows the canonical scoped-task shape — Goal, Blueprints, In/Out scope, Produces (fenced YAML listing produced interfaces), Depends on (fenced YAML with work-order and interface references), Acceptance criteria (each row carrying an ID, observation gate, and binary outcome), Gates (fenced YAML declaring which execution and LLM-as-judge gates apply). Operator-action work orders (set up OAuth, obtain sample data) are flagged at authoring time with `type: operator-action` so the orchestrator's coding-loop drain skips them; both anticipated operator actions and mid-execution discovered blockers surface in `work-orders/_external-blockers.md`. The generator short-circuits when the recorded blueprint-tree hash matches the current hash and there are no failing reviews to address. When the generator hits a decomposition ambiguity (overlapping responsibilities between blueprints, an unclear capability boundary), it appends a bare-question block to `work-orders/_questions-pending.md` and keeps decomposing. Four reviewer subprocesses run after the generator exits: structural conformance + content quality (`wo-spec-judge`), blueprint-to-work-order coverage (`wo-coverage-judge`), no-overlap of produced surface (`wo-overlap-judge`), and sequencing correctness — both structural and semantic (`wo-sequencing-judge`). Same dual completion condition and same `awaiting_clarification` exit verdict as the requirements and blueprint loops. The operator clarifies the relevant source artifact (typically a blueprint) and re-triggers.

**Stage 5 — Coding Loop (autonomous, execution-only).** Triggered by `python -m orchestrator coding-loop`. The loop drains the ready work-order queue produced by the work-orders loop in dependency order, one work order at a time. Sequence generation is not part of this loop; if blueprints have changed and the work-orders tree needs refreshing, the operator runs `python -m orchestrator work-orders-loop` first. For each work order: the orchestrator's `pick_next` walks `_sequence.md` top to bottom, returning the first work order whose `status: ready`, `blocked_by[]` are all `done`, and `type` is not `operator-action`; spawns a generator subprocess on branch `task/<wo-slug>`; the generator handles its own internal gen/review cycle, commits, pushes, and opens a PR on its first pass, then exits with a summary. On exit, the orchestrator reads the work order's `## Gates` block and spawns the gates declared `required` — tests, Playwright (when `playwright: required`), `code-spec-judge`, `code-regression-judge`, `code-security-judge`, `code-quality-judge` — aggregates their verdicts, and re-spawns the generator with aggregated feedback on any fail. If the agent discovers mid-execution that it cannot proceed without operator action, it transitions the work order to `status: blocked_external`, appends to `_external-blockers.md`, and exits cleanly; the orchestrator records and moves on. On all-pass the orchestrator posts the final summary as a PR comment and the PR is ready for operator merge; the harness never auto-merges. On merge detection during a subsequent orchestrator invocation, the work order transitions to `done`.

Handoffs between stages are discrete and operator-visible. The operator verifies the Requirements Loop's output via `git diff` before triggering the Blueprint Loop. The Blueprint Loop must reach a full `pass` (all reviewers pass and `blueprints/_questions-pending.md` empty) before the Work-Orders Loop runs. The Work-Orders Loop must reach a full `pass` before the Coding Loop drains its ready queue. Merge is always operator-driven.
