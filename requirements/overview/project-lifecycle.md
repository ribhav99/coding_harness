# Project Lifecycle

One project moves through four stages end to end: a manual PRD-authoring stage followed by three autonomous loops. Each autonomous loop uses the same core mechanic — orchestrator spawns a generator, then spawns each reviewer, aggregates verdicts, re-spawns the generator with aggregated feedback on any fail, commits the artifact on all-pass. The three loops share state-file plumbing, reviewer review files, PR-comment mirroring, and budget enforcement. They differ in generator skill, reviewer set, target artifact tree, and the completion condition.

**Stage 1 — Manual PRD authoring.** The operator opens a Claude Code session, invokes the `prd-authoring` skill, and drafts a single `PRD.md` at the project repo's root. One monolithic document in prose. The skill wears a senior-PM role with feature-unit scoping discipline, a clarification policy (ambiguous → ask and wait; specific → act; middle → propose plus up to two questions), overview-style writing rules (narrative prose, active voice, no fluff, WHAT not HOW), and no-fabrication and no-refactor-breadcrumb discipline. Critique is conversational inside the same session — the operator asks "what's missing?" or "critique this section" and the skill applies a five-category rubric (CONFLICT, MISSING, AMBIGUOUS, DUPLICATION, STALE) filtered to critical-only findings. Authoring the PRD is the human's job; there is no autonomous loop at this stage. When the PRD is ready, the operator triggers the Requirements Loop.

**Stage 2 — Requirements Loop (autonomous).** Triggered by `python -m orchestrator requirements-loop`. The generator reads `PRD.md` and decomposes it into the full structural tree under `requirements/`. Two output surfaces: product-overview sections (flat inside `requirements/overview/`) and Feature Requirements Documents (flat inside `requirements/features/`, with `<slug>_children/` subdirectories for child features). The generator is iterative — it reads any existing overview and features trees first and only edits what needs changing. When the PRD itself is genuinely ambiguous, the generator appends a structured block to `requirements/_questions-pending.md` and keeps working on everything that is not blocked. Four reviewer subagents run after the generator exits: structural spec, cross-doc consistency, PRD coverage, and feature scoping. Completion is dual: full `pass` requires all reviewers pass AND `_questions-pending.md` has no open questions blocking the review. If reviewers pass on the concrete parts but open questions remain, the loop exits `awaiting_clarification`, the artifact is committed, and the operator resolves the questions by editing `PRD.md` before re-running.

**Stage 3 — Blueprint Loop (autonomous, non-blocking bubble-ups).** Triggered by `python -m orchestrator blueprint-loop`. The generator produces feature blueprints per FRD and foundation blueprints for cross-feature concerns (auth, data model, error handling, observability). When the generator hits a decision that requires operator judgment — tech stack, framework choice, hosting model, auth provider, ORM, major architectural pattern — it does not stop. Instead it appends a structured block to `blueprints/_decisions-pending.md` with a title, one-paragraph context, two to four pre-researched options each with pros and cons, a recommended default with rationale, and a blank "Your choice:" field. The generator keeps working and drops `TBD: <decision-title>` markers where the decision matters. Four reviewer subagents run after the generator exits: structural spec, FRD-to-blueprint coverage, cross-blueprint consistency, and decision hygiene. Completion is dual: full `pass` requires all reviewers pass AND `_decisions-pending.md` has zero unanswered decisions. If reviewers pass on the concrete parts but open decisions remain, the loop exits `awaiting_decisions`, the operator resolves at their leisure, and re-running picks up where the loop left off.

**Stage 4 — Coding Loop (autonomous).** Triggered by `python -m orchestrator coding-loop`. No phases — one continuous task sequence. The loop first generates an ordered work-order sequence (once at the start, or whenever blueprints have changed as tracked by `.sequence.meta.yaml`), then drains the ready queue in dependency order. Sequence generation produces flat `work-orders/wo-NNN/` directories with `blocked_by[]` and `sort_order` fields, scoped into the standard scoped-task body, and reviewed by three reviewers (scoping, coverage, dependencies) that the orchestrator spawns after the sequence generator exits. Sequence execution runs one work order at a time: the orchestrator spawns a generator subprocess on branch `task/<task_id>`, and the generator handles its own internal gen/review cycle, commits, pushes, and opens a PR on its first pass, then exits with a summary. On exit, the orchestrator spawns six reviewer subprocesses — tests, Playwright, spec, regression, security, quality — aggregates their verdicts, and re-spawns the generator with aggregated feedback on any fail. On all-pass the orchestrator posts the final summary as a PR comment and the PR is ready for operator merge; the harness never auto-merges. On merge detection during a subsequent orchestrator invocation, the work order transitions to `done`.

Handoffs between stages are discrete and operator-visible. The operator verifies the Requirements Loop's output via `git diff` before triggering the Blueprint Loop. The Blueprint Loop must resolve all pending decisions before the Coding Loop can consume its output. Merge is always operator-driven.
