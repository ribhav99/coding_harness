# Product Description

The coding harness is a reusable kit for running long-horizon software engineering work through Claude Code autonomously, with verification as the primary correctness gate. A single operator takes a project from a drafted product description to merged pull requests without sitting inside the intermediate decomposition, scoping, and per-work-order execution stages.

The product moves a project through five stages — one manual, four autonomous. The operator opens a Claude Code session and drafts a single monolithic `PRD.md` at the project repo's root using the `prd-authoring` skill. That PRD is the only artifact the operator writes by hand. Four autonomous loops follow: the Requirements Loop decomposes the PRD into a structural tree of product-overview sections and Feature Requirements Documents; the Blueprint Loop turns approved FRDs into technical blueprints (across container, component, and feature types), surfacing architectural choices that need operator judgment as clarification questions in `blueprints/_questions-pending.md`; the Work-Orders Loop decomposes the blueprints into a flat dependency-ordered sequence of work orders under `work-orders/`, surfacing decomposition ambiguities as clarification questions in `work-orders/_questions-pending.md`; the Coding Loop drains the ready work-order queue, driving each work order through an autonomous gen/review cycle to a reviewed pull request ready for the operator to merge.

Each autonomous loop shares the same mechanic. An orchestrator spawns a generator subprocess, then spawns each reviewer subprocess, parses each reviewer's trailing `VERDICT:` line from stdout, re-spawns the generator on any failure, and commits the artifact on all-pass. The same plumbing — state files, reviewer review snapshots, PR-comment mirroring, budget enforcement — runs across all four loops. The three upstream loops (requirements, blueprint, work-orders) additionally share the communication-folder mechanism (the generator reads each reviewer's communication file directly to see prior reviews and its own prior responses) and the dual completion condition (all reviewers pass AND `_questions-pending.md` empty), exiting with a unified `awaiting_clarification` verdict when source artifacts need clarifying. The coding loop is execution-only — per-work-order subprocesses communicate through the PR (commits + comments) and reviewer stdout; there is no communication folder.

Claude Code is the runtime. The orchestrator never makes direct Anthropic API calls — every model interaction goes through `claude -p` as a subprocess. This inherits every Claude Code improvement for free and leverages the Claude Max subscription rather than per-token billing. The orchestration surface stays thin — a Python loop that spawns subprocesses and aggregates verdicts, backed by in-session hooks, skills, and subagents.

Local files are the source of truth. The canonical PRD, FRDs, blueprints, work orders, and execution state live at the project repo's root under `requirements/`, `blueprints/`, `work-orders/`, `artifacts/`, and `harness/`. The entity layout mirrors Software Factory's model so mechanical upload to SF (or any future external system) is possible. External backends are optional outbound mirrors, never alternative queues — the orchestrator always reads from and writes to local files.

The product serves one persona and is scoped accordingly. It is a personal tool for a single technical operator running Claude Code on their own projects, not a team-scale product. It does not pursue multi-user polish, cross-agent portability, autonomous PRD writing, chat-style assistant flows, or token-level cost optimization. Wall-clock throughput is the budget unit. Autonomy lives inside each loop; handoffs between loops are discrete, operator-visible gates. The PRD is human. Clarification questions during requirements, blueprint, and work-orders loops are answered by the human. Merge is human. Everything else is autonomous.
