# Technical Requirements

The harness is composed of a Python orchestrator, an on-disk artifact layout, state files, skills, hooks, and agents. Each piece has a narrow responsibility so the orchestration surface stays thin and the complexity lives in prompts and artifacts.

The **Python orchestrator** exposes `python -m orchestrator <subcommand>` as its entry point. Subcommands are `requirements-loop`, `blueprint-loop`, `work-orders-loop`, `coding-loop`, and `status`. Loops are not daemons — the operator runs one subcommand at a time. The orchestrator spawns generator and reviewer subprocesses, parses each reviewer's trailing `VERDICT:` line from stdout, manages each upstream loop's communication folder (ensure-exists, snapshot to `harness/state/reviews/<loop>/attempt-<N>/` at attempt boundaries, never wipe — the folder accumulates the full conversation across attempts and across invocations), decides retry vs pass vs exhaust, commits artifact changes on pass, materialises `.work-order.meta.yaml.blocked_by[]` from the work order's `Depends on` block on work-orders-loop pass, posts PR comments on coding-loop execution, handles the unified `awaiting_clarification` exit verdict for all three upstream loops, and detects merged PRs to transition work orders to `done`.

The **on-disk layout** lives at the project repo's root and mirrors Software Factory's entity model so that upload to SF (or any system adopting a similar shape) is mechanical. `PRD.md` at the root is the operator-authored monolithic PRD, input to the requirements loop and never edited by any autonomous loop. `requirements/` holds the generated overview and features trees with a flat node shape (a visible `<slug>.md` content file, two dotted-hidden meta files per node, and an optional `<slug>_children/` sibling directory). `blueprints/` holds three subdirectories — `containers/`, `components/`, `features/` — corresponding to the three blueprint types; each blueprint is a visible `<slug>.md` plus dotted-hidden `.<slug>.<kind>.meta.yaml` and `.<slug>.requirements.meta.yaml` meta files; feature blueprints are slug-matched 1:1 with `requirements/features/<slug>.md`. `requirements_communication/`, `blueprints_communication/`, and `work-orders_communication/` at the project root (siblings of the artifact trees) hold the gen↔reviewer communication files for the three upstream loops — append-only conversation transcripts the generator and named reviewer both read and write. `work-orders/` is flat with slug-named work-order files (`wo-<slug>.md` plus dotted-hidden `.wo-<slug>.meta.yaml` for each), a `_sequence.md` listing every work order's slug in execution order (mutable), a `_external-blockers.md` summarising operator-action and discovered-blocker work orders (regenerated on every loop run), a `.sequence.meta.yaml` tracking the blueprint hash and generation timestamp, and an `_backlog/` directory for gaps filed by the coding loop. `artifacts/` holds artifact folders by slug. `harness/` holds state and logs. Meta files are orchestrator-managed — generators write only the visible content files, and the orchestrator materialises the dotted-hidden metas after the generator exits, deriving titles from each doc's first H1 and setting IDs to `null` for later mirror sync to populate. There is no local versioning; git history is the audit trail.

**State files** under `harness/state/` are JSON. Reviewer reviews are archived under `harness/state/reviews/<loop-name>/[<task-id>/]attempt-<N>/<reviewer-name>.md` — for the upstream loops (requirements, blueprint, work-orders), the orchestrator snapshots each reviewer's communication file from the live folder at attempt boundaries (the reviewer wrote that file directly during the attempt); for the coding-loop's per-work-order execution, the orchestrator captures the reviewer subprocess's stdout and writes it to the same archive path. The entire `harness/` tree is committed to git as a first-class project artifact for audit, replay, failure-mode analysis, and future training data. State files are never deleted; log files may be pruned on a documented retention policy.

**Skills** are installed under `.claude/skills/` as short `SKILL.md` files. Skills exist in one of two shapes: tool-wrappers (reusable "here is how to do X" instructions plus a thin CLI recipe; the agent decides when, the skill documents how) and LLM-as-judge (pure prompting skills that produce a verdict). Skills are for LLM-driven work only — deterministic mechanics (state-file rotation, iteration counting, history appending, PR comment posting) live in the orchestrator, not in skills. Each skill carries its own autonomy posture: no clarifying questions mid-loop, decide and proceed. Generators write artifact files to disk. Upstream-loop reviewers (requirements, blueprint, work-orders) append their full review to their own communication file in `<loop>_communication/<reviewer-name>.md` and emit a short stdout acknowledgement ending with the `VERDICT: pass|fail` line. Coding-loop per-work-order execution reviewers, by contrast, emit their full review as their subprocess's final chat message captured by the orchestrator as stdout — they don't use the communication-folder mechanism.

**Hooks** enforce output contracts. Generator summaries end with a recognised `VERDICT:` line. Reviewer final chat messages end with a `VERDICT: pass|fail` line. **Agents** are role-specialized prompts — one generator per loop (lead PM for requirements, lead engineer for blueprints, lead tech lead for work-orders, IC for per-work-order execution) plus a reviewer subprocess per rubric.

A **local-planner module** reads and writes the on-disk layout as a single concrete class. A **mirror adapter interface** exposes one-way push hooks for status updates and comments to external systems; mirrors are outbound only. **Git operations** (branch, commit, PR open, PR comment, merge detection) are wrapped in a thin GitHub CLI layer. A reference skeleton of the on-disk layout lives at `project-template/` inside the kit repo — cloning it into a new project repo is how a new project starts.
