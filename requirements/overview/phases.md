# Phases

Ship order mirrors the operator's actual workflow — author the PRD, then iterate on the next loop. Each milestone gets a real project run-through before the next starts.

**v0.1 — PRD authoring + Requirements Loop.** The `prd-authoring` skill is fully fleshed out for monolithic PRD drafting with senior-PM posture and critique on demand. The `requirements-loop` orchestrator subcommand ships. The `prd-to-frds` generator skill runs autonomously and iteratively. All four requirements-loop reviewer skills land: `req-spec-judge`, `req-cross-doc-judge`, `req-coverage-judge`, `req-scoping-judge`. Loop-level state file and verdict parsing are in place. The `requirements/_questions-pending.md` mechanism and `awaiting_clarification` verdict are wired up with the dual completion condition (reviewers pass plus zero open questions). A `Stop` hook on reviewer subagents validates the two-line verdict format. No mirrors; local only. Exit criteria: the operator authors a PRD in a new project repo, runs `requirements-loop`, and ends up with a reviewed FRD tree they are willing to blueprint against.

**v0.2 — Blueprint Loop and non-blocking decisions.** Pin the blueprint artifact shape (on-disk layout, meta fields) based on requirements-loop learnings. The `blueprint-loop` orchestrator subcommand ships. The `frd-to-blueprint` and `foundation-blueprint-authoring` generator skills land. The `bubble-up-decision` skill appends to `_decisions-pending.md` with pre-populated options, pros and cons, and a recommended default (non-blocking). The orchestrator handles the `awaiting_decisions` verdict and the dual completion condition (all reviewers pass plus zero open decisions). All four blueprint-loop reviewers ship: `bp-spec-judge`, `bp-coverage-judge`, `bp-consistency-judge`, `bp-decision-judge`. Exit criteria: the blueprint loop produces reviewed blueprints for the v0.1 project, with at least one real bubble-up cycle (loop stops with open decisions → operator resolves → loop runs again and completes).

**v0.3 — Coding Loop sequence generation.** Pin the work-order artifact shape based on blueprint-loop learnings. The `coding-loop` orchestrator subcommand ships with sequence generation only (execution deferred). The `blueprint-to-tasks` and `scope-task` generator skills land. All three sequence-gen reviewers ship: `wo-scoping-judge`, `wo-coverage-judge`, `wo-dependency-judge`. The flat `work-orders/wo-NNN/` layout with `.sequence.meta.yaml` for blueprint-change detection is in place. Exit criteria: a reviewed, ready work-order sequence exists for the v0.2 project.

**v0.4 — Coding Loop execution (tests gate).** Per-work-order execution subprocess wired into `coding-loop`. Tests gate only; no LLM reviewers yet. Generator opens PR on first pass. State file per work order; PR comment mirroring. One work order at a time; queue drain respects `blocked_by[]` and `sort_order`. Exit criteria: the first work order is merged to `main` of the v0.3 project from an autonomous coding-loop run.

**v0.5 — Coding Loop LLM reviewers.** The `spec-judge`, `regression-judge`, `security-judge`, and `quality-judge` gates ship. The Playwright gate for UI-touching work orders ships via `run-playwright-check`. Status transitions are fully automated end-to-end across all three loops.

**v1.0 — Polish.** Software Factory mirror ships once SF has an upload API. Operator documentation lands: README, runbook, failure-mode catalog derived from the first twenty real work orders. A skill and reviewer-name consistency pass renames coding-loop execution reviewers to `code-*`. Ad-hoc operator-invokable review skills ship for each artifact type (blueprint, work order, code). An `index-updater` agent and `harness/index.md` round out the release.
