# Architecture

The project lives in a single git repo containing the operator's `PRD.md` at the root plus generated trees for `requirements/`, `blueprints/`, `work-orders/`, `artifacts/`, and `harness/` state. A reusable kit — the coding harness itself — hosts the orchestrator, skills, and agents that drive the four autonomous loops. External mirrors like Software Factory and GitHub Projects are optional outbound sync targets, never part of the read path.

Responsibilities are layered and single-owned. Manual PRD and product-overview authoring is owned by the operator working through the `prd-authoring` skill. FRD decomposition, review, and iteration is owned by the Requirements Loop. Blueprint synthesis, review, iteration, and architectural-clarification questions are owned by the Blueprint Loop. Work-order generation, scoping, and dependency-graph correctness are owned by the Work-Orders Loop. Per-work-order code execution is owned by the Coding Loop. The canonical artifacts — PRD, FRDs, blueprints, work orders — live as local files at the project repo's root.

The Python orchestrator owns next-loop selection, status transitions, budget enforcement, session lifecycle management, clarification-pause detection, and the per-loop communication-folder lifecycle. Cross-session memory and handoff context live in `harness/state/<id>.json`. In-session enforcement — verdict-trailer validation, preventing premature stop, blocking writes outside a reviewer's own communication file — lives in Claude Code hooks. Reusable capabilities (generator prompts, reviewer judges, authoring assistants) are packaged as skills. Operator-invoked entry points are slash commands. Role-specialized session prompts are agents under `.claude/agents/`. Git is ground truth about what changed; the human audit trail is GitHub PR comments plus git history, published through a sync script.

Each autonomous loop has the same shape. The orchestrator spawns a generator subprocess; when that exits, it spawns each reviewer subprocess; it parses each reviewer's trailing `VERDICT:` line from stdout; on any fail it re-spawns the generator (which reads each reviewer's communication file directly for prior reviews and its own prior responses); on all-pass it commits the artifact. Identical plumbing — state files, reviewer review snapshots, communication-folder lifecycle, PR-comment mirroring — runs across the three upstream loops (requirements, blueprint, work-orders). The loops differ in which generator skill runs, which reviewer set evaluates the artifact, which tree on disk is the target, and which file location holds open questions. All three upstream loops couple reviewer pass to an empty `_questions-pending.md` and exit with the unified `awaiting_clarification` verdict; the coding loop is execution-only and has no communication folder — per-work-order subprocesses communicate through the PR (commits + comments) and reviewer stdout.

The orchestrator drives Claude Code as a subprocess. It never makes direct Anthropic API calls. This keeps the orchestration layer thin and means every Claude Code improvement — new models, better tool use, new skills primitives — is inherited without orchestrator changes.
