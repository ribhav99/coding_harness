A pack can now hold more than one side pouch

Until now Main Body could hold exactly one component bag. A rep who needed a second one had nowhere to put it, and the back office had no way to tell one bag's contents from another. A tester hit exactly that in UAT. This change lets a rep open as many bags as they want, numbers them when there is more than one, lets them drop an empty one, and carries the numbering into the spreadsheet the back office builds from.

The work is careful and unusually well tested: one clean database change, every write path updated together, and a large set of tests that pin the awkward cases rather than the implementation. Every check I ran passes. I found no breakage. What follows is one gap on the screen a rep signs off on, one design call worth recording, and some smaller things.

Nothing has been posted to GitHub. Nothing on this branch has been touched. Decide each finding and I post exactly what you approve, in your words.

Findings

Most significant first. Each is pre-set to what I would do; change it if you disagree, and edit the wording — it goes out under your name.

1. On the screen the rep signs off, the same component in two bags shows as two identical lines with nothing to tell them apart

Medium Blocks merge: no

What breaks

Pack Review — the last read-through before a pack is sent — lists each component as code, description, brand, quantity, grouped under its section. It shows nothing about which bag a line is in. So the whole point of this feature, the same swabs in two different bags, arrives on that screen as two lines that are character-for-character identical. The rep cannot tell whether they are looking at a deliberate split across two bags or an accidental duplicate.

What Pack Review shows — Main Body

SW-4001Cellulose Swab 12mmB+L Surgical1
SW-4001Cellulose Swab 12mmB+L Surgical1

One of these is in the first bag and one is in the second. The spreadsheet says so. This screen does not.

When

Every time a rep uses the feature as intended and then reviews the pack. This is the headline case, not an edge one.

Why

Two lines for one component used to be impossible in one bag-and-section combination — anything that would have produced them was silently folded into a single line with the quantities added up. Keeping them apart is exactly what this change had to do, and it did it correctly. But nobody went back to the review screen to give the reader the one piece of information that now distinguishes them, and that screen drops it. The line already carries which bag it is in; only the row component throws it away, so this is a small fix.

Where in the product

The component list on Pack Review.

Found by: the adversarial judge; I verified it. Honest caveat: two identical rows were already possible before this change — put the same knife loose and in the tray and you got the same thing. So it is not strictly new. What is new is that it is now the normal result of using the feature, on the one screen whose job is the final check.

2. A bag's number is a position, so the same physical bag can be called something different later — and the document that says so is then frozen

Medium Blocks merge: no

What breaks

"Side Pouch 2" does not name a bag. It means "the second bag that currently holds something". Empty a bag, or drop an empty one, and every bag after it slides up a number. So a rep can spend an afternoon calling a bag "Side Pouch 3", walk to the review screen, download the spec, and hand the back office a document that calls the very same bag "Side Pouch 2" — and Pack Review shows no bag names at all, so they never see the change happen.

When

Any working session where a bag ends up empty. Bags one, two and three; the rep moves everything out of bag two; the rail keeps showing three cards while they work, because that is deliberately what stops the layout jumping under them. Then they leave the page — to review, to the dashboard, anywhere — and the empty one is forgotten, so bag three becomes bag two.

Why

Nothing stores what a bag is called. Each surface counts the bags it can see and numbers them on the spot. There is a stable internal identifier, and it is deliberately never shown — which is what keeps the numbers still mid-edit, and is also exactly why they move afterwards.

The part that makes this worth raising rather than shrugging at: the first spec download locks the pack. So a numbering the rep did not expect is not just sent, it is sealed. Correcting it means duplicating the pack and starting again.

Where in the product

Visualize & Assemble, and the spec spreadsheet the back office receives.

Found by: my own review, and independently by the architecture and adversarial judges. The request behind this work only asked for the bag limit to be lifted — the numbering is this work order's own addition, so nothing external says positional is wrong. It is a call worth recording rather than leaving implicit.

Decision

3. A bag with components in it offers no way to remove it, and no explanation

Medium Blocks merge: no

What breaks

The small × that removes a bag appears only on an empty one. On a bag holding anything there is nothing at all — no greyed-out control, no tooltip, no hint. A rep who has decided a whole bag should not exist has to work out for themselves that the path is to move every component out, one at a time, before a remove control appears.

When

A rep sets up three bags for a customer, the customer changes their mind about one, and the rep wants it gone.

Why

An empty bag exists only in the browser, so dropping it costs nothing and needs no decision. A bag with components in it would need someone to have decided what happens to them — do they move somewhere, or go away with the bag — and that decision has not been made. Stopping at "empty only" is reasonable. Showing the rep nothing at all is the part worth fixing, and a disabled control with one line of explanation is cheap.

Where in the product

The Main Body bag cards in the configurator rail.

Found by: my own review, corroborated by the requirements judge.

4. The spreadsheet works out its bag numbers separately, from a different set of bags

Low Blocks merge: no

What breaks

The pull request says every surface names a bag through one shared piece of code. The spreadsheet does not — the server works it out independently, and from a different set: it counts only bags that hold something, while the screen counts every bag the rep can see, empty ones included. There is a test pinning the screen's rule and a test pinning the server's. Nothing compares the two.

When

Not observably today, as far as I can reproduce: the screen is rebuilt from scratch on the way to the download, which erases the empty bags before the two rules can be seen to disagree. This is finding 2 wearing different clothes — the same missing notion of a bag having a name. Worth its own line because the pull request states the opposite, and the next person to change one rule will not know there is a second.

Why

The spreadsheet is built on the server and cannot call the browser's code, so the rule had to be written twice. That much is unavoidable. Describing it as one place is what invites someone to change one half.

Where in the product

The pack spec download on Pack Review.

Found by: my own review; both the regression and adversarial judges reached the same place. The adversarial judge rated it high on the basis that the two disagree at the moment of export — I could not reproduce that, because the screen state that disagrees is gone before a download is possible. Downgraded on that basis.

5. This is a narrower version of a design the backlog already specifies

Design Blocks merge: no

What breaks

Nothing today. But there is an existing, written, ready-to-build work order that specifies containers as real things a rep can add, remove and number in any section, persisted like anything else. This instead stamps a number onto every component line, for one kind of bag only, and keeps empty bags in the browser. When the bigger design lands it removes what was added here, redoes the same sweep through every module, and changes the naming rules under reps who have got used to these.

When

Whenever the container-instance work is picked up. The author is aware — the code points at it as pending — but the trade is not written anywhere a reader of the merged history would find it.

Why

The request behind this is a real UAT failure that needs unblocking now, and the full design is large. Shipping the narrow thing first is a perfectly normal call. The repo's own rule is that deviating is fine as long as it is called out, so it reads as a choice rather than drift. That call-out is what is missing.

Where in the product

Not user-facing. It is about what the next person to touch this pays.

Found by: the architecture judge, which called it a blocker. I disagree on severity — unblocking UAT with a narrow, coherent, well-tested change is the right trade; the gap is that it is undeclared.

6. The pack's history cannot say which bag anything moved to

Low Blocks merge: no

What breaks

Every move of a component from one bag to another is recorded as the words "moved to another side pouch". No from, no to. A move into a bag from elsewhere records only "container set to Side Pouch", with no number.

When

Someone reviewing a finished pack asks why the swabs ended up where they did, or support is reconstructing what a rep changed after a complaint.

Why

The stored data is faithful — the identifier is recorded on both sides of every move. It is the reading of it that is lossy: the number people see is worked out from the pack as it is now, so a history row from last week cannot be translated into it. Falls straight out of finding 2. Not a regression: before this change there was only ever one bag, so there were no moves between bags to record.

Where in the product

The activity list on Pack Review.

Found by: the architecture and adversarial judges; verified by me.

7. An empty bag looks like a change to the pack but only lives in the browser, and nothing caps how many you can open

Low Blocks merge: no

What breaks

A rep clicks "+ Add side pouch" and gets a titled card with its own delete button and a live drop zone. Everything about it says "I changed this pack". Leave the page and it is gone, with no message. Alongside that there is no cap: the button now shows unconditionally, so holding it down fills the rail with empty cards, each drawn again in both pack views.

When

A rep opens two bags to plan a layout before filling them, gets interrupted, and comes back to a page that has forgotten one.

Why

An empty bag has nothing to store — it is only "a bag" because a component mentions it — so it is remembered only while the page is open. Deliberate and documented, and the previous single-bag behaviour worked the same way. It just gets more noticeable now a rep can open five. Note the "two reps see different bags" version of this is not reachable: a pack is only editable by the rep who owns it.

Where in the product

The configurator rail.

Found by: my own review, and the architecture judge.

Decision

8. Two new pieces of the write interface have no caller — and if they stay unwired, adding a component can only ever reach the first bag

Low Blocks merge: no

What breaks

Two of the three ways a client can say "which bag" were added and validated, but nothing sends them — not the app, not any script, not the importer. Only the third has a caller. There is a real consequence hiding behind that: because adding a component can never name a bag, a component added while a rep is looking at their third bag lands in the first one, and they have to drag it. And if a caller ever did name the bag kind without a number, it would land at the lowest slot, pushing every existing bag's number up.

When

The unreachable part costs nothing at runtime; it costs the next reader, who has to establish that two of three write paths are dead before trusting anything about them. The add-lands-in-bag-one part is a live rep-facing rough edge on a multi-bag pack.

Why

Symmetry — it looks odd for one write path to accept something the other two do not. The house rule here is blunt: if code is dead, delete it, no exceptions. So it is one decision or the other, not both: wire it up so an add can target a bag, or delete it and accept that adds always land in the first bag.

Where in the product

Adding a component to a pack that has more than one bag.

Found by: the architecture judge for the dead half, the adversarial judge for the lands-at-the-front half; I confirmed no caller exists anywhere in the repo.

Decision

Nits

Six. None change what the program does. Never applied by me and never posted as separate comments — at most one batched line in the summary.

6 nits — mention or skip?
  1. Every bag carries a "which position am I" number that is worked out for it and then thrown away — it is read in exactly one place, which re-derives it by searching the list anyway. To make that search possible the whole list of bags is passed down into two components that do not draw it, and the same two-line unwrap is repeated at six call sites.
  2. The description on the new "section — container" text says it is the format the pack spec prints. The spec builds its own version on the server and never reads this one; the only thing that uses it is the toast after adding a component.
  3. Six comments explain a bug from an earlier draft of this same branch ("an earlier round had each counting its own pouches", "counting them here is what once let…"). Once this is squashed there is nothing to look up. The invariant each states is worth keeping; the anecdote is not.
  4. The database change validates its new range check immediately, which takes a brief exclusive lock and reads every existing row. Almost certainly imperceptible at current volumes; worth knowing if the table ever gets large.
  5. On the server the three-part slot is passed as three separate arguments through six or more signatures and returned as a five-element tuple, where the browser half of the same feature introduced a named type for it and reads noticeably better.
  6. The comment on the new column states "only a side pouch ever carries more than one" as though the database enforces it. The database only checks the value is at least one; the rest is an application rule. Either say so, or add the check.
