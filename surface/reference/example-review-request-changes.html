Toasts over overlays, and the dashboard tab

by Rowan G · 11 files, +352 / −23 · frontend only, no backend, no migration

Two unrelated bug fixes. One: a toast's close button was dead whenever a modal or the cart was open, so the toast just sat there until it timed out. Two: going into a pack from the Packs tab and clicking "Dashboard" to come back dropped the rep on Accounts instead of Packs.

Both root causes are correctly diagnosed and both bugs are genuinely fixed. The problem is the price of the first fix: making the toast clickable also makes it absorb clicks, and the toast sits exactly on top of the cart's action buttons.

Recommendation: request changes — on one finding.
The work order for this task explicitly said to make the toast dismissable "without letting it block interaction with the overlay beneath it." This does exactly that, and the PR describes the blockage as unavoidable. It isn't — there's a small, contained change that gets both halves. Everything else here is a comment.

Findings

Most significant first. Each is verified against the code — judge claims I couldn't reproduce were dropped and are listed at the bottom.

F1 · The toast eats clicks on the cart's buttons

medium blocks merge
What breaks

With the cart open, a toast covers the cart's main action buttons and swallows any click aimed at them. Not "clicks the wrong thing" — nothing happens at all, for the four seconds the toast is on screen (plus about half a second more while it fades out invisibly).

When

A rep opens the cart and presses "Add to this pack". If that fails — a component that can't be resolved, a conflict, a server error, a dropped connection — the app raises an error toast and deliberately leaves the cart open so the rep can retry. The toast lands on the retry button it is telling them to press. The same thing happens for the app-wide error toast appearing over any open dialog.

Why

The cart slides in from the right and puts its buttons at the bottom of that panel — bottom-right of the screen. Toasts also appear bottom-right. They overlap almost exactly.

Previously the toast was "transparent" to the mouse: it looked like it covered the button, but the click passed straight through and the button worked. This change makes the toast solid to the mouse so its own close button works — and a solid toast catches everything else too. A second part of the change then stops that click from travelling anywhere else, so it dies on the toast.

It is avoidable. Only the toast's own close and action buttons need to be solid. The rest of the toast can stay transparent, letting clicks through to the cart button underneath as before. That shrinks the blocked area from roughly the size of a business card to the size of the little "×". Nothing is lost: swiping a toast away and hovering to pause it were already impossible while a modal was open, both before and after this change.

Where in the product

The shopping cart panel, and any dialog with buttons in its bottom-right corner.

Found by: me, and independently by the regression, design and spec reviewers. Verified against the cart's layout, the toast library's defaults, and the underlying overlay library's source.

What breaks

The next person who reads that table to decide how to remember something. They'll be told this category of memory is wiped when the page reloads. For the dashboard tab, it isn't.

The new row says the remembered value "resets on reload." F3 · The comment recording the trade-off names the wrong trade-off

medium does not block
Late addition — the last reviewer returned after the rest of this page was written, and found this. I verified every part of it against the library source.
What breaks

The PR asks reviewers to eyeball one specific behaviour change and weigh whether it's acceptable. That change is described backwards. The menus the PR says are now affected aren't; the one it says is safe isn't. The same wrong description is written into a code comment, which is what the next person to touch this will read and believe.

When

A rep has any dropdown open — the "⋯" menu on a pack row, the user menu in the top bar, a toolbar filter, a picker — and clicks a toast. Those menus used to close and now stay open, on a page that is otherwise frozen, until they press Escape or pick an item. The PR states these are unaffected. Meanwhile the one kind of overlay the PR says will now linger — a hover-card style popover — still closes exactly as before.

Why

The PR's description rests on a category error. It calls dropdowns and pickers "non-modal", but in this codebase they are all modal — the library makes that the default and nothing here overrides it. And the comment says clicks are the only way an overlay decides to close; there is a second way, based on where keyboard focus moves. The change only blocks the first. The popover it expected to linger closes through the second channel, because clicking a toast moves focus onto it.

There is a supported fix for both. The overlay library ships a way to mark a region as "part of the family — clicks and focus landing here are not outside." It covers both channels in one registration, and the library's own toast component uses exactly this. I confirmed it works from where our toast sits, outside every dialog, because the registry is app-wide rather than nested.

The honest counterweight: reaching it means importing from an entry point the library literally labels "internal", or promoting a sub-package to a direct dependency. That is a real cost and a fair reason to keep what's here — in which case the comment and PR text just need correcting, which is the cheap half of this finding.

The main fix — clicking a toast doesn't close the cart or a dialog behind it — is solid and unaffected by any of this.

Where in the product

Every dropdown in the app, while a toast is showing.

Found by: the design reviewer (the library primitive) and the adversarial reviewer (the inversion). I confirmed both in the library source: dropdowns and pickers default to modal with no override anywhere in our code, and the popover's focus path is only suppressed when a click was seen first — which this change guarantees never happens.

F4 · Nothing realistic checks the half of the fix that rewrites the address bar

low does not block
What breaks

If the part that writes the tab into the address bar quietly stopped working, no test anywhere would notice.

When

A future refactor touches the dashboard, the address-bar write stops happening, everything stays green, and the "tab survives a reload" behaviour is gone without anyone noticing until a rep reports it again.

Why

Two browser tests were widened to tolerate the new address, but they were widened in a way that accepts both the old and the new form — and the check they use stops at the first match, which is the old form, before the rewrite even lands. So they can never observe it. The one test that does observe it has to switch off a safety in the test harness that the real app doesn't have, so it's checking behaviour under a setup that differs from production.

Why this is low and not medium: the actual reported bug — the breadcrumb losing the tab — is fixed by the in-memory half alone and is well covered. What's untested is the bonus of also surviving a reload. Worth noting only because one of those two widened tests walks the exact path the bug was reported on, so it's the natural place to assert the tab rather than shrug at it.

F5 · A test safety was switched off for a whole file, not just the new tests

low does not block
What breaks

Nothing today — the whole suite is green. This is a trap laid for later: the dashboard's test file can now start failing intermittently, in tests nobody touched, for reasons that won't point back here.

When

Whenever a future test happens to finish at the wrong moment. The symptom would be a dashboard test failing on a search or page-number value it never set — the kind of flake people re-run rather than diagnose.

Why

The address-bar library queues its writes in one shared place for the entire test process. Its test harness clears that queue between tests precisely so one test can't leave a pending write for the next one. The PR needed that clearing off for its new tests — reasonably — but switched it off in the shared setup helper, so it's also off for the roughly two hundred lines of existing dashboard tests above, which drive search terms, sorting and page numbers through that same queue. Moving the switch onto just the new block closes it.

Where in the product

Nowhere — this is test infrastructure only.

6 nits — mention as one line, or skip?
  • Switching tab writes the address bar twice instead of once. Harmless — but the reason it isn't three times is a build-time optimiser silently papering over the fact that this code reads a value that can change out from under it. Fragile in a way that won't be obvious later.
  • On Safari the second write is delayed by up to a third of a second, so switching tab and immediately opening a pack can leave a stray tab marker on the pack's address. Cosmetic, but it rides along on any link shared from there.
  • A mistyped tab in a shared address (wrong capitalisation, a typo) silently falls back to whatever tab that browser last used and rewrites the address to match, rather than falling back to the default.
  • The fix is pointer-only: with a dialog open, someone using the keyboard or a screen reader can hear the toast but still can't reach or dismiss it. Pre-existing, not caused here — but the PR states the problem as solved.
  • The new file names its starting-value constant differently from the two files it was modelled on, and it's the only page-level hook in the repo that reaches sideways into a components folder.
  • Third near-identical copy of the same "remember this for the session" boilerplate, comment template included. The README now names the pattern but there's still no single place it lives. And the two halves of the toast fix sit in different files with neither mentioning the other.

8 things I checked and threw out — including one reviewer's "blocker"
"Screen-reader users can't reach the toast under a modal"

Simply false. The library that hides the rest of the page from screen readers makes a specific exception for live announcement regions, which is exactly what the toast area is. No accessibility defect.

"The tab fix should have reused the existing come-back-to-where-you-were mechanism" — called a blocker by one reviewer

The author already considered and rejected this, with a good reason: going dashboard → pack → edit → back to the pack loses the trail, so the tab would be lost again. The reviewer's counter-example (landing on a remembered tab after logging in) can't happen — signing in reloads the whole app, which clears the memory. Rejected.

"Making the toast solid creates a click-hijacking risk"

Backwards. The old behaviour was the risky one: an opaque toast visually covering a confirm button while the click went straight through to it. This PR is an improvement on that axis. It's the reason F1 is a trade-off rather than a pure regression.

"The address-bar write could land on the wrong page"

Would need a page change within a single tick of arriving. Not reachable by a human.

"The new README row contradicts the coding rules file"

It does, but that contradiction predates this PR — the README already listed more categories than the rules file.

"The README table formatting is broken"

It isn't; the formatter is happy and the columns are consistent. The diff just renders it oddly.

"Stacked or hidden toasts become clickable" / "the toast corner becomes a click shield"

Neither. The library's own rule for hidden toasts is more specific and still wins, and the container around the toasts has no height of its own.

"Keyboard users still can't reach the toast under a modal"

Real and confirmed — the dialog's focus trap yanks focus back, so the toast is unreachable by Tab and by the toast library's own keyboard shortcut. But it predates this PR. Demoted to a nit line rather than dropped outright, because the PR presents the problem as solved and it's solved only for the mouse.
